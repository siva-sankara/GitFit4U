3. PROMOTION SCOPES AND ELIGIBILITY

Gym offers apply only to membership purchases for their owning gym. Platform
offers apply only to GETFIT4U platform purchases. Public gym offer/ad queries
exclude platform and review-required offers. The normal Owner management
endpoints still require the current authorized gym; Admin inspection does not
remove those restrictions.

Only an Admin with admin:platform permission can create/update platform offers.
The server sets scope, publisher, version and one-time application. Platform
billing follows the existing per-gym subscription. Registration applicants can
view offers only through their own persisted registration; renewals require
the current owned gym and validate the expected gym context.

Eligibility checks status, dates, owner, gym, platform plan, MONTHLY/YEARLY
period, NEW/RENEWAL purchase kind, minimum purchase and redemption limits.
Empty audience/plan selections mean all otherwise eligible purchases. Selected
owner, gym and plan restrictions must all match. Purchase history enforces
new-subscription-only restrictions. Listing is paginated; checkout repeats the
authoritative validation, so display alone never grants a discount.

Only one discount can be selected. Automatic stacking and recurring discounts
were not introduced. An offer without a custom code can be selected using its
public reference from the Apply action. Prices come from configured platform
plans, use integer minor currency units and existing rounding, and retain the
existing tax treatment. Invalid or unsupported payable totals are rejected.

4. MIGRATION AND FINANCIAL SAFEGUARDS

The scope migration considers gym ownership, creator permissions/assignments,
membership plans and existing purchase relationships. Clearly gym-bound offers
are backfilled as GYM_MEMBERSHIP, including legitimate Admin-created gym offers.
Missing/conflicting relationships become REVIEW_REQUIRED for explicit review;
unbound old offers are not guessed to be active platform discounts. Updates
compare the observed revision and are safe to rerun. No deletion, financial
amount/status change or issued-invoice rewrite is part of this migration.

Read-only dry-run against the configured database returned:
  mode: dry-run
  scanned: 2
  gymMembership: 2
  reviewRequired: 0
  updated: 0

The apply operation was exercised only in the isolated test database. Production
application has not been run. Deployment steps from the backend directory:
  npm.cmd run db:migrate-promotion-scopes
  Review the counts and investigate any REVIEW_REQUIRED records.
  npm.cmd run db:migrate-promotion-scopes -- --apply
  Use the established index migration/deployment process to create the new
  non-unique scope/status/date index; existing npm.cmd run db:migrate also
  performs notification/OTP index maintenance, so retain its maintenance-window
  procedure rather than treating it as a scope-only operation.

Payment snapshots preserve original amount, discount, tax, total and applied
offer reference/version. Checkout, payment-history detail and existing invoice
generation use these committed values. An existing pending order is resumed at
its committed amount; checkout locks offer changes once that order exists.

Offer reservations participate in the existing payment transaction and serialize
competing use of a limited offer. Existing order retries and captured-payment
redemption remain duplicate-safe. A signed delayed capture after an offer edit
or expiry honors the committed payment, creates one invoice and redeems once.
Subsequent purchases do not inherit a one-time discount. Offer edits or pauses
invalidate stale uncommitted discounted quotes.

Pending orders remain pending and have no paid invoice. Existing authorized
Admin cash/UPI collection and payment-pending activation are preserved; an
offer or activation override does not itself record money as collected.

7. PROFILE PHOTO AND VIEWER BEHAVIOR

Profiles use one shared avatar variant: 6rem mobile and 8rem desktop; compact
list/table avatars remain separate. The profile header wraps names/actions and
stats with enlarged text. Existing Avatar consumers in lists, messages, reviews,
attendance and support gain the same viewer when an authorized photo exists.
Header navigation avatars retain their existing profile-link behavior.

The viewer prefers the provided full-size avatar URL over its thumbnail and
uses natural-size, viewport-bounded object-fit: contain rendering, without
circular cropping or forced enlargement of small images. It provides visible
Close, image-click, backdrop-click and Escape dismissal, a loading state and
safe error text. It uses the existing accessible portal, focus trap/restoration,
modal stacking and background-scroll lock. Click/double-click/Enter/Space events
do not activate the containing member row; editing controls are separate.

Only image URLs already authorized and supplied by existing APIs are used. No
private bucket is made public, no new image lookup bypasses tenant permissions,
and no viewer-specific persistent image cache is added. Account-session changes
close an open photo. Existing S3 access and service-worker privacy rules remain.

8. CONFIRMED INSTALL-BUTTON CAUSE

The startup action was labeled Install even when no saved beforeinstallprompt
event existed; that branch opened the guidance modal. This is the confirmed
code path behind an instructions-only action being presented as direct install.
Absence of an event can be legitimate browser/installability behavior.

The existing PWA lifecycle already started at application level, outside the
banner. This update additionally captures the event with an early same-origin
head script before the application module and adopts it into the shared
controller. That closes a possible bundle-loading timing gap; a missed event
on the user's specific device was not proven. No unsupported claim that adding
a manifest alone fixed installation is made.

9. SUPPORTED INSTALL FLOW AND LIMITATIONS

When the browser provides an unused beforeinstallprompt event, the UI shows
Install. A direct click synchronously calls the real event's prompt() before
unrelated asynchronous work, clears the saved event and shares its busy state
across banner/Settings. Subsequent clicks cannot reuse it. Dismissed/error states
are handled. Prompt acceptance alone is not reported as verified installation;
appinstalled or detectable standalone mode controls installed UI state.

Without a supported event, the action is explicitly How to install and explains
the applicable browser's manual route. The shared controller survives route
changes and banner expiry. The session banner remains dismissible, above the
navbar and limited to two minutes; Profile/Settings remains available afterward.
No event object is serialized into localStorage.

Manifest identity/start URL/scope/standalone settings, icon assets, early script
ordering and existing root service-worker behavior were inspected/tested. The
root worker remains coordinated with Firebase; no private API, message or
invoice cache was introduced. Login/session restoration and tab ordering remain.

Automated tests synthesize browser install events and verify exact prompt calls;
they do not install an app on a physical device. Real Android/Chromium prompt,
home-screen icon and standalone launch, and iPhone manual installation remain
unverified. No configured signed native release/store destination was established;
native app distribution would require a separate deliverable.
